# Referral Credits

Usage credits an organization receives when a member redeems another member's referral code. Credits are spent before the organization's budget.

## How it works

- Every profile gets a referral code (`OXY-XXXXX`), generated by the database on insert.
- A new member redeems a code with `POST /management/credits/redeem`. Both organizations, the referee's and the referrer's, receive a credit of `REFERRAL_CREDIT_AMOUNT_USD`.
- The referrer's award is clamped so their balance never exceeds `REFERRAL_MAX_PER_REFERRER_USD`.
- On each request, `core/budget.py` burns credits first; whatever the credits do not cover is charged to the budget as usual.

## Configuration

| Variable | Meaning |
|---|---|
| `REFERRAL_CREDIT_AMOUNT_USD` | Credit awarded to each side per redeemed code |
| `REFERRAL_MAX_PER_REFERRER_USD` | Upper bound on a referrer's credit balance |

Defaults live in `packages/engine/routes/credits.py`. An invalid value falls back to the default with a warning in the log.

## Endpoints

- `GET /management/credits/balance`: the organization's current credit balance.
- `POST /management/credits/redeem`: redeem a code (rate limited to 5 per minute).
- `GET /management/credits/referral-link`: the caller's referral link, built from `SITE_URL`.

## Abuse checks

- Self-referral and circular referral are refused (database trigger `fn_prevent_self_referral`).
- One redemption per profile.
- Email aliases are normalized (`user+tag@`, dotted Gmail addresses) before the self-referral check.
- Redemptions from the same IP within 24 hours are refused.

## Limits

- Credits are a usage balance inside the gateway, not money: they cannot be withdrawn or moved between organizations.
- Balances live in Redis and last as long as Redis data does; `profiles` records the referral itself (`referred_by`, `credits_earned`). The award is several writes, not one transaction, so a crash midway can award one side only.

For general caveats, see `docs/product/known-gaps-and-non-goals.md`.
